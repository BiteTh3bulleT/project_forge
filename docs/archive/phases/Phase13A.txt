Implement Phase 13A: Storage Backend Foundation.

Scope: LIVE_INFRA / STORAGE_FOUNDATION / DEFAULT_SQLITE.

Postgres, Redis, and Qdrant are now managed services in Docker, but live application storage still uses SQLite.

This phase introduces the storage backend foundation required for future migration.

Do not migrate live memory to Postgres yet.
Do not make Postgres the default backend.
Do not remove SQLite.
Do not dual-write live data yet.
Do not wire Qdrant into live retrieval yet.
Do not wire Redis into live queues/caches yet.
Do not change public APIs.
Do not add routes.
Do not alter live memory semantics.
Do not alter gateway/modelruntime/retrieval behavior.
Do not make Redis or Qdrant canonical truth.
Do not make vector hits admissible evidence.
Do not make FORGE-K live authority.

Purpose:

The Docker stack now includes:

- Postgres for future durable relational storage
- Redis for future ephemeral coordination
- Qdrant for future vector retrieval acceleration

This phase adds the explicit application-side backend boundary:

- storage backend config
- Postgres connection scaffolding
- migration runner structure
- backend capability contracts
- parity test strategy
- no-default-switch guarantees

Core doctrine:

- SQLite remains the default live store.
- Postgres is future durable relational storage.
- Redis is ephemeral only: cache, queue, pub/sub, locks, streams.
- Qdrant is vector acceleration only, not truth.
- SQLite/Postgres remain provenance/inspectability source of record.
- Qdrant vectors and scores cannot bypass policy, Courthouse, Consensus Mesh, Context Compiler, memory usefulness evidence, or Kernel authority.
- No backend switch happens without explicit tests and rollback.
- All storage migration must preserve authority boundaries.
