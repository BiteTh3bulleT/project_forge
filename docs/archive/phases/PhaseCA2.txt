## Audit Method

Use a multi-pass audit.

## Pass 1 — Repo Inventory

Map the repo structure.

Identify:

- apps
- services
- packages
- scripts
- Nix files
- Tauri/Rust files
- Go core files
- frontend TypeScript/React files
- docs
- tests
- generated files
- archived/legacy files
- prompt packs
- worktree leftovers
- evidence folders

Document what appears active, legacy, generated, test-only, simulator-only, or unknown.

## Pass 2 — Compare Against CA1

If CA1 exists, read it first.

Compare current repo state against CA1 findings.

Classify CA1 items as:

- resolved
- still present
- partially resolved
- worsened
- stale finding
- needs operator decision
- unable to verify

Do not assume CA1 was correct. Verify against current code.

## Pass 3 — Duplicate Detection

Search for duplicate or conflicting implementations.

Check for duplicate:

- API routes
- route handlers
- service startup paths
- gateway/tool execution paths
- memory write paths
- modelruntime paths
- approval paths
- auth/security middleware
- desktop shell stores
- taskbar/window/native-app registries
- terminal/file/browser launchers
- CSS blocks
- type definitions
- config loaders
- Nix modules/profiles
- scripts
- docs describing the same authority differently
- status reports with conflicting truth claims

Classify duplicates as:

- intentional compatibility wrapper
- test fixture
- simulator-only
- legacy retained for provenance
- real duplicate requiring cleanup
- dangerous duplicate runtime path

Do not delete anything during this audit.

## Pass 4 — Truncation and Corruption Scan

Search for signs of truncated or corrupted files.

Look for:

- files ending mid-sentence
- incomplete Markdown sections
- unclosed code fences
- unclosed JSON/YAML/TOML/Nix structures
- malformed imports
- broken JSX/TSX blocks
- broken Go/Rust syntax
- repeated pasted blocks
- merge conflict markers
- “truncated”
- “omitted”
- “rest of file”
- “continue here”
- “TODO: finish”
- placeholder ellipses in executable code
- dangling references to missing files

Explicitly scan for:

- <<<<<<<
- =======
- >>>>>>>
- TODO
- FIXME
- HACK
- STUB
- MOCK
- PLACEHOLDER
- DUMMY
- FAKE
- NOT_IMPLEMENTED
- panic("TODO")
- unimplemented!
- todo!
- throw new Error("not implemented")
- lorem ipsum
- sample data
- hardcoded demo data

Classify each finding by severity.

## Pass 5 — Placeholder, Mock, and Fake Runtime Audit

Identify all placeholders, mocks, demo data, and fake behavior.

Mocks are acceptable in:

- tests
- simulator-only packages
- fixture folders
- explicit demo docs

Mocks are not acceptable in:

- live runtime paths
- production API routes
- desktop shell behavior
- gateway/tool execution
- approval decisions
- memory writes
- modelruntime production flows
- system status surfaces that claim real state
- desktop taskbar/native-app lifecycle state

For every mock/placeholder finding, record:

- file path
- line or section
- whether it is test-only, simulator-only, docs-only, or runtime
- risk
- recommended action

Run the repo’s normal validation commands.

Attempt:

- npm run lint
- npm run validate:js
- npm run validate:desktop
- npm run validate:local
- npm run build
- npm run build:core
- npm run build:desktop

Also attempt focused checks where relevant:

- npm -w @forge/desktop run build

- nix flake check if Nix is available
- nix build .#forge-core if Nix is available
- nix build .#forge-desktop-shell if Nix is available

If a command cannot run due to environment limitations, record:

- command
- reason it could not run
- exact error
- whether this blocks confidence

Do not mark blocked checks as passed.

## Pass 7 — Runtime Authority Boundary Audit

Check for accidental authority expansion.

Verify:

- FORGE-K simulator services are not used as live daemon authority unless explicitly documented and tested
- model output does not directly mutate canonical memory/state
- semantic writes go through Control Lane/syscall/journal paths
- gateway/tool execution does not bypass approval/audit systems
- desktop shell does not run direct host mutation commands
- shell UI does not expose systemctl, nixos-rebuild, reboot, shutdown, package install, model load/unload, or destructive cleanup controls
- memory/state/history separation remains intact
- simulator-only code is labeled and isolated

Flag any live path that violates authority boundaries as Critical.

## Pass 11 — Fix Queue

Create a prioritized fix queue.

Use severity:

- Critical — breaks build, corrupts runtime truth, unsafe authority bypass, live mock pretending to be real, data loss risk
- High — duplicate runtime path, stale endpoint, major broken UI path, failing core validation
- Medium — placeholder panel, dead code, stale docs, partial test coverage
- Low — cleanup, naming, comments, cosmetic duplication

For each finding, include:

- ID
- severity
- category
- file path
- summary
- evidence
- impact
- recommended fix
- estimated difficulty
- whether safe for automated fix
- whether operator decision is needed
